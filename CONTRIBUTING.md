# Contributing to the CCF docs

Thanks for helping with the docs. This page covers how the docs are versioned, how to change them, and how pull requests get reviewed and merged. For how to write a page, see [STYLE.md](STYLE.md). To build the site locally, see the [README](README.md).

## How the docs are versioned

Each CCF repository has its own release cycle, so each one gets its **own versioned docs instance**: one Docusaurus docs plugin instance per repository (`api`, `ui`, `agent`, and one per plugin), each with its own versions and version dropdown. The general pages (introduction, OSCAL, glossary) stay in `docs/` and aren't versioned.

> The site is moving to this layout. Until an instance has pages, its content lives in `docs/` and isn't versioned.

The instances are declared in [`instances.yaml`](instances.yaml), and its schema is [`scripts/instances.schema.json`](scripts/instances.schema.json). Each entry names the repository, the instance `id`, its `kind` (`product` or `plugin`), the folder (`path`), the URL (`route`), the `label`, and for a plugin the policy repositories that belong to it. An instance without pages yet isn't built, so it has no navbar item until its first pages land.

Each instance's sidebar is `sidebars/<id>.ts`. `yarn start` and `yarn build` generate it, listing every page in the instance's folder and, for an instance with `openapi`, a link to its newest **API reference**. To curate one, delete the first line (the "Generated by" comment) and commit the file; the generator then leaves it alone. A curated sidebar must keep the id `main`, which the navbar links to.

`yarn build` publishes an instance's newest released lines only: as many as `build.onlyIncludeVersions` in `instances.yaml` allows for its kind. Its `current` docs are published only until its first line is released; `yarn start` always shows them.

For an instance with the id `api`, the files are:

| Path | What it holds |
|---|---|
| `api/` | `current`: the unreleased ("next") docs for the next release |
| `api_versioned_docs/version-0.21/` | The released `0.21` line |
| `api_versioned_sidebars/` | The sidebar of each released line |
| `api_versions.json` | The released lines, newest first |
| `openapi/api/0.21.yaml` | The `0.21` OpenAPI spec, copied unchanged from the api's `docs/swagger.yaml` at the release tag. Its reference page is `/api/0.21/reference`, which Redoc renders in the browser. The page shows a display copy that the build writes to `.docusaurus/` (`scripts/openapi-display.mjs`): schemas nested more than 4 `$ref` levels deep are collapsed to their name, because Redoc runs the browser out of memory on the full api spec. Never edit the spec to make it render; its download button serves it unchanged |

### One version per minor line

A version is a **minor line** such as `0.21`, never a patch such as `0.21.1`.

- **A patch release** (`0.21.1`) edits its line in place, in `api_versioned_docs/version-0.21/`, and adds its notes to that line's release notes. It doesn't cut a new version.
- **A minor or major release** (`0.22.0`) cuts a new version from `current`:

  ```sh
  yarn docusaurus docs:version:api 0.22
  ```

  Before that command, because the cut copies `current` as it is:

  1. For `api`, add the line's OpenAPI spec as `openapi/api/0.22.yaml`, copied unchanged from the api's `docs/swagger.yaml` at the tag. The sidebar's **API reference** link points to the newest spec, and the cut freezes it.
  2. For `api`, `ui` and `agent`, regenerate the configuration reference:

     ```sh
     node scripts/gen-config-ref.mjs --instance api --ref v0.22.0 --previous v0.21.0
     ```

     It reads the instance's code at the tag with `gh`, and fails until `scripts/config-ref/<id>.yaml` describes every setting the release defines. It reads the api's `cmd/root.go`; the ui's `src/defaultconfig.json`, `src/stores/config.ts` and `env.d.ts`; and the agent's `cmd/` folder, with the api's `pkg/agentconfig/types.go` at the version the agent's `go.mod` requires.

### Plugins and the catalog

Each released plugin has its own instance: `plugin-aws-ecr` lives in `plugins/aws-ecr/` and `plugin-aws-ecr_versioned_docs/`, and is served at `/catalog/aws-ecr`. The **Catalog** page (`/catalog`) lists every plugin with its newest release and links to it. A plugin instance has no navbar link of its own, only a version dropdown that shows on its pages.

[`scripts/sync-catalog.mjs`](scripts/sync-catalog.mjs) writes the plugin pages and the catalog from GitHub:

```sh
node scripts/sync-catalog.mjs
```

It reads the org's repositories with `gh` and never writes to GitHub. For every unarchived `plugin-*` repository that isn't a `*-policies` bundle and has a final release, it:

1. adds an entry to `instances.yaml` if the plugin has none;
2. writes the plugin's page, `index.md`, from its README at that release, in the [plugin page](STYLE.md#plugin-page) layout, with the [policies catalog](STYLE.md#policies-catalog) of the bundles its entry lists (each at its newest final release, with the controls its policies' `METADATA` lists);
3. edits the page of that release's minor line in place, or cuts the line with `docusaurus docs:version:<id> <line>` when it's new;
4. writes `src/data/catalog.json`, which the Catalog page renders.

The pages are generated: change the plugin's README or the script, not the pages. `--dry-run` reads GitHub and prints the report without writing anything.

A plugin's policy bundles are the ones its `policies` list in `instances.yaml` names. Write that list by hand: bundle names don't always match their plugin's, so the script never maps a bundle by name. It ends with the released bundles no plugin lists; add each one to its plugin's `policies` once you know where it belongs, and run the script again. A bundle release only changes its row: run the script again, and it never cuts a plugin version.

### Where to make a change

- **A fix that's true for a released line:** edit that line's `*_versioned_docs/version-<line>/` pages. If it's also true for the next release, make the same change in `current`.
- **Anything for an unreleased change:** edit `current` only.
- **Never edit a released line other than the one you're fixing.** A pull request for one release touches only that release's line.
- **Released lines are read-only history otherwise.** Don't reword, restructure or "tidy" old lines.

Release docs (notes, API reference, configuration reference, feature and upgrade guides, catalog rows and version cuts) are mostly written by the factory when a release ships. You can still open a pull request for any of them.

## Pull requests

1. Branch from `main` and keep each pull request to one change: one release, one fix or one new page.
2. Follow [STYLE.md](STYLE.md) for voice, page skeletons, media and links.
3. Run `yarn build` before you push. A broken internal link fails the build.
4. Open the pull request against `main` and say what changed and which version lines it touches.

Every push to `main` deploys the site, so a merged pull request goes live once that deploy finishes.

## The factory and the `factory:hold` label

The CCF factory opens, reviews and merges docs pull requests for releases. It only merges pull requests it opened itself, after its reviewer approves them and the build passes. On pull requests that people open, it only reviews.

To make the factory wait, add the **`factory:hold`** label to the pull request. The factory leaves a docs pull request with that label alone: it won't merge it while the label is on. Remove the label when you're done and the factory carries on.

Two other labels also stop the merge:

- `do-not-merge`: don't merge this pull request, whoever asks.
- `factory:stop`: the factory takes no further action on this pull request at all.

The factory only acts on these labels. It doesn't read comments for instructions such as "please wait".
